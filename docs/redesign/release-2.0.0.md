## 2. สิ่งที่เปลี่ยนเบื้องหลัง

- ตรวจ login ซ้ำฝั่ง server ทุกหน้า (ADR-13) หน้าจึงเป็น dynamic และมี query นับลูกค้าค้างชำระ 1 ครั้งต่อการเปิดหน้า (ตัวเลขบนเมนู)
- CSP: เพิ่ม origin ของ Supabase ที่ตั้งตอน build (บน production อยู่ใน `*.supabase.co` อยู่แล้ว ผลเท่าเดิม)
- Viewport: `interactive-widget=resizes-content` (คีย์บอร์ดดันปุ่มบันทึกขึ้นมาแทนการบัง)
- ลบ v1 CSS และโค้ดที่ไม่ใช้ (CSS ที่โหลด ~92 KB → ~60 KB) · ฟอนต์เหลือ 4 น้ำหนัก
- Dev เท่านั้น: Playwright 1.63.0 + @axe-core/playwright 4.13.0 และ CI job `e2e`

**ผล:** เจ้าของแจ้ง "ผ่าน" 2026-10-18 บน Preview ของ `v2.0.0-rc.1` (รายงานผลรวม ไม่ได้แยกรายข้อ)

Preview ใช้ฐานข้อมูล staging กดบันทึก/ลบ/เคลียร์ยอดได้จริงโดยไม่กระทบร้าน

- [ ] พ่อ/แม่ลองบันทึก 1 รายการโดยไม่มีคนช่วย แล้วเล่าว่าติดตรงไหน

## 5. ลำดับขึ้น production

1. เจ้าของผ่าน UAT → bump `2.0.0` บน `release/2.0.0`
2. PR `release/2.0.0` → `main` แบบ **merge commit** · ไม่มี SQL ต้องรันก่อน · merge ตอนร้านปิด
3. ตรวจ production (login, ภาพรวม, บันทึก 1 รายการแล้วลบ ทำโดยเจ้าของ) → tag `v2.0.0` บน SHA ที่ deploy
4. Back-merge `main` → `develop`
5. เพิ่ม `e2e` เป็น required check ใน ruleset ของ `main`

## 6. ย้อนกลับ

Vercel → Deployments → deployment ของ `v1.2.0` (`b5213db`) → **Instant Rollback** · ไม่ต้องทำอะไรกับฐานข้อมูล (v2.0.0 ไม่มี migration) · ข้อมูลที่บันทึกด้วย v2.0.0 ใช้กับ v1.2.0 ได้ (โครงสร้างเดียวกัน)
